## 先给结论：Codex的正确用法是“小任务、可审查、能回滚”

Codex不是把一句“帮我把项目做好”丢进去就结束。比较稳定的第一次使用顺序是：

1. 核对官方入口和当前版本；
2. 打开一个可回滚的项目副本或 Git 分支；
3. 先让 Codex 阅读目录并复述任务；
4. 只允许它修改明确的文件范围；
5. 运行最小测试或构建；
6. 查看差异，再决定是否合并。

如果你还没有安装 CLI，可以先看 [Codex CLI安装与Windows/macOS配置](/guides/codex-cli-install-npm-windows-macos-china-guide-2026-08)；如果只是寻找官方下载入口，参考 [Codex官方下载地址与真假辨别](/guides/codex-download-official-address-windows-macos-verify-2026-09)。

## Codex有哪些使用入口

搜索“Codex怎么用”时，常见混淆是把网页、桌面 App、CLI 和第三方中转服务当成同一个东西。先按工作方式选择：

| 入口 | 适合任务 | 开始前要确认 |
| --- | --- | --- |
| 官方网页或云端工作区 | 讨论需求、查看任务、处理云端项目 | 当前账号、项目权限和官方页面 |
| 桌面 App | 图形化管理会话、项目和任务 | 下载来源、系统支持和本地权限 |
| Codex CLI | 在终端读取项目、改文件、跑测试 | Node/安装方式、PATH、登录方式 |
| 第三方网页服务 | 国内环境中的独立代码或多模型体验 | 服务主体、数据保存、模型标称和密钥边界 |

官方 Codex 信息可从 [OpenAI Codex产品页](https://openai.com/codex/)、[OpenAI开发者平台](https://developers.openai.com/) 和 [官方 GitHub 仓库](https://github.com/openai/codex)交叉核对。搜索结果中带有“官网”“国内版”“免费版”的页面，不因为标题这样写就自动成为官方来源。

## 第一次使用：先让Codex读项目，不要马上改代码

打开项目后，第一条指令应该让工具建立上下文，而不是直接生成大量代码。可以使用下面的任务模板：

```text
请先阅读当前项目，不要修改文件。
输出：
1. 技术栈和启动命令；
2. 入口文件与主要模块；
3. 当前测试或构建命令；
4. 完成“目标任务”可能涉及的文件；
5. 你准备采取的步骤和潜在风险。
目标任务：为登录表单增加客户端必填校验，但不改变接口协议和页面布局。
```

好的响应应当包含目录、证据和计划，而不是只给一段看起来完整的代码。发现它误解项目时，先纠正上下文，再开始修改。

## 第二步：把需求写成可验收的小任务

Codex更适合有边界的工程任务。一个合格的任务至少包含以下信息：

| 要素 | 示例 |
| --- | --- |
| 目标 | 为注册表单增加邮箱格式校验 |
| 范围 | 只修改 `src/components/RegisterForm` 与对应测试 |
| 不改变 | 不改后端接口、路由和视觉布局 |
| 验收标准 | 空值、非法邮箱、合法邮箱各有测试 |
| 验证命令 | `npm test -- RegisterForm` 或项目实际命令 |
| 完成信号 | 测试通过，并列出修改文件和剩余风险 |

不要同时提出“升级依赖、重构目录、换 UI、修复所有测试”四个大目标。任务越大，越难判断哪一个改动造成回归。

## 第三步：确认修改范围和权限

让 Codex 写文件前，先确认以下边界：

- 当前目录是不是正确项目，不是用户主目录或生产挂载目录；
- 工作区是否有未提交改动；
- 是否已经创建 Git 分支或备份；
- 工具能读写哪些目录；
- 是否禁止删除文件、安装依赖或访问网络；
- 测试是否会修改数据库、发送邮件或调用真实第三方接口。

如果工具提出安装新依赖，先看包名、版本、许可证和维护来源。对于未知脚本、未知下载器和要求输入密钥的安装页，不要仅凭“Codex完整版”或“国内版”字样执行。

## 第四步：让Codex修改后立即给出差异

修改完成后，不要只看一句“已完成”。要求它输出：

```text
请停止继续修改，先汇报：
1. 修改了哪些文件；
2. 每个文件解决了什么问题；
3. 是否新增或删除依赖；
4. 运行了哪些命令及结果；
5. 尚未验证的风险。
```

然后人工查看 `git diff` 或 IDE 的变更面板。重点检查：是否改到了任务范围之外、是否覆盖了用户已有改动、是否把密钥或本地路径写进代码、是否悄悄降低了权限校验。

## 第五步：运行测试和构建，区分失败类型

Codex可以帮助分析错误，但“它说测试通过”不能替代终端真实输出。常见失败可以这样分流：

| 现象 | 优先排查 | 处理方式 |
| --- | --- | --- |
| `command not found` | PATH、Node或包管理器 | 重开终端，确认版本与安装路径 |
| 模块找不到 | 依赖未安装、锁文件或工作目录 | 对照项目锁文件，避免随意升级全部依赖 |
| 测试断言失败 | 需求理解、边界条件或旧测试 | 先定位首个失败断言，再补最小修复 |
| 权限或认证失败 | 环境变量、账号、项目权限 | 不打印密钥，回到官方设置页核对 |
| 网络请求超时 | 本地网络、代理或服务状态 | 先做离线测试，再看官方状态页 |
| 构建成功但页面异常 | 浏览器控制台、资源路径和运行时配置 | 用实际构建产物检查，不只看退出码 |

一次只处理一个根因。连续让工具“再试一次”容易把可定位的问题变成一串未经审查的改动。

## Windows和macOS使用时的区别

Windows 用户常见问题是 PowerShell、PATH、项目目录和代理只对浏览器生效；macOS 用户则常见于 shell 配置文件、Node 版本和权限提示。两边都建议：

1. 先运行版本和帮助命令，确认调用的是预期程序；
2. 在目标项目目录执行，而不是在随机目录执行；
3. 记录实际运行命令，但隐藏密钥和私人路径；
4. 修改 `.env` 后重启当前进程；
5. 先用没有敏感数据的示例项目验证。

CLI 登录、OAuth 回调和 API Key 问题可参考 [Codex CLI登录失败排查](/guides/codex-cli-login-oauth-callback-api-key-proxy-troubleshoot-20260826)。不要把浏览器能登录等同于终端已经获得相同的项目权限。

## 国内环境下如何判断问题在哪一层

“Codex国内版怎么用”通常包含多个不同问题：官方页面打不开、CLI装不上、账号没有入口、模型不可选，或者第三方平台与宣传不一致。建议按层排查：

| 层级 | 现象 | 证据 |
| --- | --- | --- |
| 入口 | 找不到官网或下载页 | openai.com、developers.openai.com、github.com/openai |
| 本地环境 | 命令不存在、安装失败 | Node版本、PATH、包管理器输出 |
| 网络链路 | 登录回调或 API 超时 | 终端代理、浏览器访问和官方状态页 |
| 账号权限 | 能登录但没有某入口或模型 | 当前账号、项目和官方页面提示 |
| 第三方服务 | 名称、额度或接口与宣传不一致 | 服务条款、平台文档和实际测试 |

第三方服务可以作为独立备选，但不能修复 OpenAI 官方账号权限，也不能证明某个模型获得官方授权。使用第三方代码工具时，先用公开仓库或脱敏片段测试，避免上传客户数据、私有密钥和生产代码。

## 一个可复用的Codex工作流

```text
需求 -> 读取项目 -> 复述计划 -> 创建分支 -> 小范围修改
     -> 单元测试 -> 构建/静态检查 -> 查看差异 -> 人工Review -> 合并
```

对于数据库、支付、部署、权限和删除操作，再增加人工确认步骤。即使工具能执行命令，也不代表它知道业务后果。

## 常见问题

### Codex适合新手吗？

可以，但新手更应该从小项目和可回滚分支开始。先让它解释目录、命令和改动，再逐步放大任务范围。

### Codex能不能一次重构整个项目？

技术上可能提出大范围修改，但不建议第一次就这样做。应拆成模块、测试和构建都能单独验证的小任务。

### Codex是否等于ChatGPT网页版？

不完全等同。两者可能存在账号或产品关联，但使用入口、工作区、权限和可执行能力不同，需以当前官方页面为准。

### “Codex国内版”安全吗？

不能只看名称判断。应核对服务主体、域名、隐私规则、密钥处理、数据保存和撤销方式，任何要求提交官方密码或 API Key 的陌生页面都应谨慎。

### Codex修改错文件怎么办？

立即停止继续修改，保留当前差异，使用 Git diff、撤销或分支恢复到可确认的状态。不要让工具在不清楚原始状态时继续覆盖文件。

### Codex可以访问生产服务器吗？

除非经过明确的权限设计、备份和人工审批，否则不建议。开发工具应默认使用隔离环境和最小权限。
